## 1. 배경

이 앱은 사내 차량 4대의 운행 기록을 관리한다. 현재 MVP 상태이며 인증이 전혀 없다.
이 문서는 실제 소스 코드를 읽고 확인한 사실만을 근거로, 사내 업무 시스템으로
수년간 쓸 수 있는 수준까지 올리는 설계를 정의한다.

### 1.1 확정된 운영 조건

인터뷰로 확정한 전제다. 설계 판단의 대부분이 여기서 나온다.

| 항목 | 확정 내용 | 설계에 미친 영향 |
|---|---|---|
| 사용자 구글 계정 | **일부 직원은 구글 계정을 못 쓴다** | 구글 로그인 기반 인증안 전부 폐기 |
| 사용 인원 | 10명 이하, 관리자 1명 | 사용자 관리 UI 불필요. 시트 직접 편집 |
| 기존 운행 기록 | **없음 (테스트 기록뿐)** | 스키마 마이그레이션 부담 소멸 |
| 제출처 | 사내 관리용이 전부 | 국세청 양식·운행구분 필드·PDF 전부 불필요 |
| 인증 방식 | **공용 암호 1개 + 이름 선택** (사용자 선택) | 개인 계정·비밀번호 변경 화면 없음 |

### 1.2 감사에서 확인한 실제 상태

**문서가 코드를 과대 서술하고 있다.** README와 SECURITY_PLAN이 주장하는 다음 기능은
코드에 존재하지 않는다. 이 설계서는 코드를 기준으로 한다.

| 문서 주장 | 실제 |
|---|---|
| 주행거리 자동 계산, 출발/도착 계기판 검증 | 계기판 1칸뿐, 거리 수기 입력 (`index.html:82-91`) |
| 실시간 통계 대시보드 | 없음 |
| 실시간 검색·필터링 | 없음 |
| CSV 내보내기 (UTF-8 BOM) | **코드에 없음** |
| LocalStorage 사용 | 커밋 `a80fa29`에서 제거됨. 현재 API 전용 |
| 운행구분(업무용/출퇴근/비업무용) | 스키마에 없음 |

`.env`, `.env.example`, `APP_SECRET_KEY`는 **어떤 코드도 읽지 않는다.** 빌드 단계도
서버도 없는 정적 사이트라 동작에 관여하지 않는다. `.env.example`이 참조하는
Firebase·Vite·Maps 키는 전부 미사용이다.

### 1.3 현재 보안 상태

세 가지가 겹쳐 운행 기록 전체가 인터넷에 열려 있다.

1. GitHub 저장소가 공개 (`github.com/cade-beep/vehicle-log-app` → HTTP 200, 미인증)
2. 라이브 `/exec` URL이 `config.js`에 평문 커밋 (`raw.githubusercontent.com` → HTTP 200, 커밋 `785fa5b`)
3. 백엔드에 신원 확인이 전무 (`Code.gs:5-6` "Who has access: Anyone")

URL을 아는 누구나 전 기록 조회·위조 등록·영구 삭제(하드 삭제, 복구 불가)가 가능하다.

**긴급도 판정: 중간.** 지울 실데이터가 아직 없어 최악의 결과가 "테스트 기록 삭제 +
Apps Script 쿼터 소모"다. 즉시 대응이 아니라 실운영 데이터 투입 전까지 인증을 붙이고
배포 URL을 새로 뽑으면 된다. 다만 쿼터 낭비 방지를 위해 저장소 비공개 전환은
지금 하는 편이 좋다. 저장소를 비공개로 돌려도 URL은 이미 공개 git 히스토리에 있으므로
**배포 URL 교체가 유일한 실질적 차단**이다.

### 1.4 이미 잘 되어 있어 유지할 것

과소평가하면 회귀를 부른다. 다음은 손대지 않는다.

- `LockService.tryLock(10s)` — 생성·삭제 양쪽에 정상 적용 (`Code.gs:106,143`)
- 서버측 검증 11개 필드 (`validateLogInput_`) — 프론트 검증에만 의존하지 않음
- `escapeHTML` 테이블 렌더 전 구간 적용
- `Content-Type: text/plain` 으로 preflight 회피 — Apps Script CORS 제약의 정확한 우회
- 15초 타임아웃 + `AbortController`, `visibilitychange` 백그라운드 폴링 중단,
  `isRefreshing` 중복 방지, 렌더 시그니처 비교로 깜빡임 방지

## 2. 목표 아키텍처

```
브라우저 (Cloudflare Pages, 정적, 빌드 없음)
  │  POST only, Content-Type: text/plain;charset=utf-8   ← preflight 회피
  │  body: { action, token, ...payload }                 ← 토큰은 헤더가 아닌 본문
  ▼
Apps Script /exec  (Execute as: Me, Access: Anyone)
  │  HMAC 서명 토큰 검증 → { 이름, 권한, 만료 }
  ▼
Google Sheets  (운행일지 / 사용자 / 차량 / 감사로그)
```

### 2.1 왜 헤더가 아니라 본문에 토큰을 넣는가

`Authorization` 헤더를 붙이면 브라우저가 CORS preflight(`OPTIONS`)를 보낸다.
Apps Script 웹앱은 `OPTIONS`에 응답할 수 없어 모든 요청이 실패한다.
`Content-Type: text/plain` + 본문 토큰은 "simple request" 조건을 만족해 preflight가
발생하지 않는다. 현재 코드가 이미 쓰고 있는 구조이며 그대로 유지한다.

### 2.2 채택하지 않은 대안

**Cloudflare Worker 인증 프록시** — Worker에 비밀을 숨길 수 있으나, 사용자를 Worker에
인증시키는 문제가 그대로 남는다. 결국 같은 인증 로직을 Worker로 옮기는 것뿐이고
구성요소만 하나 늘어난다. 보안 이득 없이 운영 복잡도만 증가하므로 기각.

**Apps Script가 HTML까지 서빙(HtmlService)** — 동일 출처가 되어 CORS 문제가 사라지지만,
구글 로그인을 쓸 수 없는 이 조직에서는 인증 이점이 없고, 기존 UI와 Cloudflare Pages
배포를 버려야 한다. 기각.

## 3. 인증 및 인가

### 3.1 비밀의 위치

암호는 **Apps Script Script Properties에만 존재한다.** 저장소·프론트엔드·시트
어디에도 없다. 관리자가 편집기에서 `setPasscodes(staffPw, adminPw)`를 한 번 실행해 심는다.

| Script Property 키 | 내용 |
|---|---|
| `PASSCODE_SALT` | 랜덤 16바이트 base64 |
| `STAFF_PASSCODE_HASH` | 직원 암호를 salt와 함께 SHA-256 10,000회 반복 해시 |
| `ADMIN_PASSCODE_HASH` | 관리자 암호, 동일 방식 |
| `TOKEN_SECRET` | 랜덤 32바이트 base64. 토큰 서명키 |
| `TOKEN_VERSION` | 정수 문자열. 올리면 전 세션 즉시 무효화 |

`setPasscodes`는 평문 암호를 어디에도 남기지 않는다(로그 포함).

### 3.2 세션 토큰 — 서버 저장 없는 HMAC 서명 방식

```
payloadB64 = base64UrlEncode(JSON.stringify({ n: 이름, r: 권한, e: 만료epoch초, v: 토큰버전 }))
sig        = base64UrlEncode(HmacSHA256(payloadB64, TOKEN_SECRET))
token      = payloadB64 + "." + sig
```

검증 순서: 서명 재계산 → **상수시간 비교** → `e` 만료 확인 → `v`가 현재
`TOKEN_VERSION`과 일치하는지 확인.

`CacheService`를 쓰지 않는 이유: 최대 TTL이 6시간이고 예고 없이 축출되어 사용자가
갑자기 튕긴다. 서명 토큰은 저장소도 만료 정리 코드도 필요 없다. 개별 세션을 미리
무효화할 수 없다는 점이 대가이나, 공용 암호 체계에서는 무효화할 개별 신원이 애초에
없다. 전원 무효화는 `TOKEN_VERSION` 증가로 처리한다.

세션 유효기간 **12시간**. 클라이언트는 `localStorage`에 토큰을 보관한다.

### 3.3 로그인 흐름 — 2단계

이름 목록을 미인증 상태로 내주면 직원 명단이 유출된다. 그래서 두 단계로 나눈다.

```
1) login  { passcode }        → { token(이름 없음), role, users[], vehicles[] }
2) bind   { token, name }     → { token(이름 포함) }
```

`bind`는 전달된 이름이 `사용자` 시트에 실제로 있고 `사용여부=TRUE`인지 검증한다.
이후 모든 요청은 이름이 들어간 토큰을 쓴다.

**이름 없는 토큰(`n`이 빈 문자열)은 `bind` 이외의 어떤 action에서도 거부한다.**
`login`만 통과한 상태로 `create`나 `delete`를 부를 수 없다. 이 검사를 빠뜨리면
감사 로그의 사용자 칸이 비어버린다.

### 3.4 권한

| 동작 | USER | ADMIN |
|---|:---:|:---:|
| 목록 조회 (ACTIVE만) | ✅ | ✅ |
| 등록 | ✅ | ✅ |
| 수정 | ✅ | ✅ |
| 삭제 (소프트) | ✅ | ✅ |
| 삭제된 기록 조회 | ❌ | ✅ |
| 복구 | ❌ | ✅ |
| 감사 로그 조회 | ❌ | ✅ |

권한은 토큰의 `r` 필드에서만 읽는다. 클라이언트가 보낸 어떤 값도 권한 판단에 쓰지 않는다.

### 3.5 무차별 대입 방어

- 로그인 실패 시 `Utilities.sleep(500)` — 초당 2회 상한
- `CacheService`에 실패 카운터. 10분 내 10회 실패 시 10분간 `RATE_LIMITED` 반환
- 실패는 감사 로그에 `LOGIN_FAIL`로 기록 (**암호 값은 절대 기록하지 않는다**)

카운터가 캐시 축출로 초기화될 수 있다는 것이 알려진 상한이다. 500ms 지연이 1차 방어이고
카운터는 보조다.

### 3.6 doGet 차단

현재 `doGet`은 무인증으로 전 기록을 반환한다. **데이터를 반환하지 않고 항상
`UNAUTHORIZED`를 반환하도록 바꾼다.** 조회는 `POST { action:'list', token }`으로만 가능하다.

## 4. 데이터 모델

### 4.1 `운행일지` 시트 (기존 13열 → 20열, **추가 전용**)

`getHeaderIndex_`가 열 위치가 아니라 **헤더 이름**으로 매핑하므로 열 순서는 코드에
영향을 주지 않는다. 이 성질을 이용해 **기존 열을 옮기지 않고 뒤에 붙이기만 한다.**
기존 셀 값이 물리적으로 이동하지 않으므로 마이그레이션 중 데이터가 어긋날 여지가 없다.

**기존 1~13열 — 위치 그대로 유지**

| 열 | key | 헤더 | 변경 |
|---|---|---|---|
| A | `id` | 기록ID | 불변. 신규 발급만 UUID로 |
| B | `date` | 운행일 | — |
| C | `departTime` | 출발시간 | — |
| D | `arriveTime` | 도착시간 | — |
| E | `driver` | 운전자 | 실제 운전한 사람 (자유 입력) |
| F | `endOdometer` | **`계기판(km)` → `도착계기판(km)`** | **헤더명만 변경.** 값은 그대로 |
| G | `distance` | 운행거리(km) | 서버 계산 전용으로 성격 변경 |
| H | `destination` | 목적지 | — |
| I | `purpose` | 운행사유 | — |
| J | `passengerCount` | 인원 | — |
| K | `fuelCost` | 단가/주유금액 | — |
| L | `vehicleNo` | 차량선택 | 검증 출처가 하드코딩 → `차량` 시트 |
| M | `createdAt` | 작성시각 | 불변 |

기존 `odometer`를 `endOdometer`에 대응시킨 것은 의미상 맞다 — 지금까지 직원이 적어온
계기판 값은 **운행을 마치고 본 숫자**다.

**신규 14~20열 — 뒤에 추가**

| 열 | key | 헤더 |
|---|---|---|
| N | `startOdometer` | 출발계기판(km) |
| O | `updatedAt` | 수정시각 |
| P | `createdBy` | 작성자 |
| Q | `updatedBy` | 수정자 |
| R | `status` | 상태 (`ACTIVE` / `DELETED`) |
| S | `deletedAt` | 삭제시각 |
| T | `deletedBy` | 삭제자 |

입력 폼과 목록의 **표시 순서는 출발 → 도착**이다. 시트의 물리적 열 순서와 무관하다.

`driver`와 `createdBy`를 모두 둔다. 남의 운행을 대신 입력하는 경우가 있어 둘은 다를 수 있다.

### 4.2 마이그레이션

실데이터가 없음을 확인했으므로 `setupSheet()` 실행 한 번으로 끝난다.

- 기존 테스트 행은 **지우지 않는다.** 신규 열이 공란으로 남는다.
- **`status`가 공란이면 `ACTIVE`로 취급한다.** 이 기본값 덕분에 legacy 행이 목록에서
  사라지지 않는다. 소프트 삭제 도입 시 가장 흔한 데이터 소실 경로를 막는다.
- F열은 헤더 문자열만 `계기판(km)` → `도착계기판(km)`으로 바뀐다. **셀 값은 움직이지 않는다.**
- legacy 행은 `startOdometer`가 공란이다. 이런 행은 **`distance`를 재계산하지 않고
  기존 값을 그대로 유지한다.** 재계산 규칙(§6)은 `startOdometer`가 있는 행에만 적용된다.
- 되돌리기: F열 헤더를 `계기판(km)`으로 되돌리고 N~T열을 지우면 원상 복구된다.
  기존 A~M열 데이터는 한 번도 이동하지 않았으므로 손실이 없다.

### 4.3 `사용자` 시트

`이름 | 권한 | 사용여부` — 권한 열은 B안에서 사용하지 않으나(권한은 암호로 결정)
장래 개인 계정 전환 시를 위해 자리를 둔다. `사용여부=FALSE`면 이름 선택 목록에서 제외된다.

### 4.4 `차량` 시트

`차량번호 | 차량명 | 사용여부` — 초기값 `0704`, `8318`, `1213`, `5486`.

- 프론트 차량 드롭다운은 로그인 응답의 목록으로 채운다.
- 백엔드는 쓰기 시에만 이 시트로 검증한다. **읽기·표시에는 검증하지 않는다** —
  나중에 `사용여부=FALSE`가 된 차량의 과거 기록이 계속 보여야 하기 때문이다.
- **하드코딩 3곳을 전부 제거한다**: `index.html:37-40`, `app.js:71`, `Code.gs:30`.

### 4.5 `감사로그` 시트

`시각 | 동작 | 기록ID | 사용자 | 권한 | 상세`

동작: `CREATE` `UPDATE` `DELETE` `RESTORE` `LOGIN_FAIL`
상세에는 변경 전후 요약을 넣되 **암호·토큰은 절대 기록하지 않는다.**

감사 기록은 해당 뮤테이션과 **같은 `LockService` 구간 안에서** 쓴다. 별도 락을 잡으면
기록만 남고 데이터는 안 바뀌는(또는 그 반대) 불일치가 생긴다.

## 5. API 표면

모든 요청은 `POST`, `Content-Type: text/plain;charset=utf-8`, 본문은 JSON.

| action | 권한 | 요청 | 응답 |
|---|---|---|---|
| `login` | — | `{passcode}` | `{token, role, users[], vehicles[]}` |
| `bind` | 토큰 | `{token, name}` | `{token}` |
| `list` | USER | `{token, includeDeleted?}` | `{data[], count}` |
| `create` | USER | `{token, ...필드}` | `{data}` |
| `update` | USER | `{token, id, ...필드}` | `{data}` |
| `delete` | USER | `{token, id}` | `{data:{id}}` — 소프트 |
| `restore` | ADMIN | `{token, id}` | `{data}` |
| `audit` | ADMIN | `{token, limit?}` | `{data[]}` |

`includeDeleted=true`는 ADMIN이 아니면 무시하고 ACTIVE만 반환한다(에러 아님).

### 5.1 오류 코드

| code | status | 클라이언트 동작 |
|---|---|---|
| `UNAUTHORIZED` | 401 | 토큰 삭제 후 로그인 화면 |
| `FORBIDDEN` | 403 | 메시지 표시, 로그인 유지 |
| `RATE_LIMITED` | 429 | 대기 안내 |
| `VALIDATION_ERROR` | 400 | 메시지 표시 |
| `NOT_FOUND` | 404 | 목록 새로고침 |
| `BUSY` | 503 | 재시도 안내 |
| `SERVER_ERROR` | 500 | 일반 메시지. **스택 트레이스 노출 금지** |

## 6. 거리 계산 규칙

```
distance = endOdometer - startOdometer     (서버가 계산)
```

- **클라이언트가 보낸 `distance`는 받지도 않고 버린다.** 서버가 항상 다시 계산한다.
- `endOdometer < startOdometer` → `VALIDATION_ERROR` 거부
- `startOdometer < 0` 또는 `endOdometer < 0` → 거부
- `distance == 0` → 거부 (운행하지 않은 기록)
- `distance > 1000` → **클라이언트에서 경고만** 띄우고 저장은 허용 (장거리 출장 존재)
- 클라이언트는 두 값 입력 즉시 거리를 실시간 표시한다. 표시용일 뿐 전송하지 않는다.

**신규·수정 기록에는 `startOdometer`가 필수다.** 위 규칙은 전부 신규 쓰기에 적용된다.
`startOdometer`가 공란인 legacy 행(§4.2)은 읽기 시 `distance` 기존 값을 그대로 쓰고
재계산하지 않는다. 단, 그 행을 **수정**하면 두 계기판 값이 모두 요구되고 그 시점부터
일반 규칙을 따른다.

**이어쓰기 자동입력:** 차량 선택 시 그 차량의 가장 최근 `endOdometer`를 출발 계기판에
자동으로 채운다. 목록이 이미 메모리에 있으므로 추가 API 호출이 없다. 실제 계기판과
다르면 사용자가 고칠 수 있다.

## 7. 클라이언트 기능

### 7.1 필터 (§11)

전량 클라이언트 측 처리. 백엔드 변경 없음.

- 기간 (시작일 ~ 종료일)
- 차량 (전체 / 개별)
- 운전자 (전체 / 개별 — 기록에 존재하는 이름으로 목록 생성)
- 텍스트 검색 (목적지 + 운행사유 부분일치, 대소문자 무시)
- **초기화 버튼** 하나로 전부 해제

### 7.2 통계 (§12)

**필터가 적용된 집합**에서 계산한다. 전부 클라이언트 측.

- 총 건수, 총 주행거리, 총 주유금액
- 차량별 주행거리 / 주유금액
- 운전자별 주행거리

### 7.3 CSV 내보내기 (§14)

현재 존재하지 않으므로 신규 구현.

- **필터된 집합만** 내보낸다 (화면에 보이는 것과 파일이 일치)
- UTF-8 **BOM(`\uFEFF`) 필수** — 없으면 엑셀에서 한글이 깨진다
- RFC4180: 쉼표·따옴표·줄바꿈 포함 시 따옴표 감싸기, 내부 따옴표 두 번
- 숫자 열(계기판, 거리, 인원, 주유금액)은 따옴표 없이 숫자로 유지
- 파일명 `운행일지_YYYYMMDD-YYYYMMDD.csv` (필터 기간 반영)
- 정적 사이트이므로 `Blob` + `<a download>` 로 그냥 받아진다 (샌드박스 iframe 아님)

### 7.4 인쇄 (§15)

**PDF 라이브러리를 도입하지 않는다.** 공식 제출 양식이 없고 사내 관리용이므로
`@media print` 블록으로 충분하다: 폼·버튼·네비 숨김, 테이블 전체 폭, 배경 제거.

### 7.5 수정 (§7)

- 각 행에 `수정` 버튼. 누르면 폼에 기존 값이 채워지고 `수정 취소` 버튼이 나타난다
- **같은 행을 in-place 업데이트한다.** 삭제 후 재생성하지 않는다
- `id`, `createdAt`, `createdBy` 불변. `updatedAt`, `updatedBy` 갱신
- 실패해도 기존 행이 손상되지 않는다 (락 안에서 단일 `setValues`)

### 7.6 삭제·복구 (§8)

- 삭제는 `status=DELETED` + `deletedAt`/`deletedBy` 기록. **물리 삭제 코드를 제거한다**
- 기본 목록은 ACTIVE만 표시
- ADMIN은 "삭제된 기록 보기" 토글로 조회하고 복구할 수 있다

## 8. 폴링 및 동시성

### 8.1 폴링 (§19)

현재 구조가 이미 요구사항 상당 부분을 만족한다. **주기(30초)를 바꾸지 않는다.**
유지: `visibilitychange` 백그라운드 중단, `isRefreshing` 중복 방지, 렌더 시그니처 비교.

추가: 폴링 응답이 `UNAUTHORIZED`면 폴링을 멈추고 로그인 화면으로 전환한다.
(만료된 토큰으로 30초마다 실패 요청을 보내는 것을 막는다.)

### 8.2 동시성 (§20)

`LockService.tryLock(10000)`을 유지한다. **제거하지 않는다.**
`update`, `delete`, `restore`도 동일하게 락 안에서 수행한다.
행 탐색은 인덱스가 아니라 `id`로 한다 — 소프트 삭제라 행이 밀리지는 않지만,
동시 삽입 중 `getLastRow()` 변화에 영향받지 않기 위함이다.

ID 충돌: 현재 `log-yyyyMMdd-HHmmss-####`(난수 4자리)는 같은 초 동시 생성 시
1/9000 확률로 충돌한다. **`Utilities.getUuid()`로 교체한다.** 기존 ID 형식의 행은
그대로 유효하다(문자열 비교만 하므로).

## 9. 배포 및 보안 헤더

### 9.1 `_headers` (Cloudflare Pages)

기존 4개 헤더를 유지하고 CSP를 추가한다.

```
Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self' https://cdn.jsdelivr.net; font-src https://cdn.jsdelivr.net; connect-src https://script.google.com https://script.googleusercontent.com; img-src 'self' data:; base-uri 'none'; form-action 'none'; frame-ancestors 'none'
```

`script.googleusercontent.com`이 반드시 필요하다 — Apps Script `/exec`는 실제 응답을
이 도메인으로 리다이렉트한다. 빠뜨리면 모든 요청이 CSP에 막힌다.

### 9.2 배포 URL 교체

인증 구현 완료 후 **새 배포를 만들어 새 `/exec` URL을 발급받고** `config.js`를 갱신한다.
기존 URL은 공개 git 히스토리에 남아 있어 되돌릴 수 없다.
아울러 GitHub 저장소를 비공개로 전환한다(쿼터 낭비 방지).

인증이 붙은 뒤에는 URL 노출이 치명적이지 않다 — 암호 없이는 아무것도 못 한다.
URL 교체는 심층 방어이지 주된 대책이 아니다.

### 9.3 문서 정리

- `README.md`, `SECURITY_PLAN.md`를 실제 구현과 일치하도록 다시 쓴다
- `.env.example` **삭제** — 아무것도 읽지 않는 죽은 파일이며, 존재 자체가
  "비밀 관리를 하고 있다"는 잘못된 인상을 준다
- 로컬 `.env`는 건드리지 않는다 (gitignore 대상이며 사용자 소유)
- `BILLING_PLAN.md`는 대체로 정확하므로 폴링·페이로드 수치만 검증 후 유지

## 11. 테스트

### 11.1 정적 검사 (매 단계)

`Code.gs`는 Apps Script 전역 API를 메모리로 흉내 낸 Node 하네스에서 로드·실행해
문법과 로직을 검증한다. `app.js`는 `node --check`.

### 11.2 보안 테스트 (P1 이후 매 단계 반복)

| 시도 | 기대 결과 |
|---|---|
| 토큰 없이 `list` / `create` / `update` / `delete` | `UNAUTHORIZED` |
| `doGet` 직접 호출 | 데이터 없이 `UNAUTHORIZED` |
| 서명 조작 토큰 | `UNAUTHORIZED` |
| 만료된 토큰 | `UNAUTHORIZED` |
| `TOKEN_VERSION` 증가 후 기존 토큰 | `UNAUTHORIZED` |
| USER 토큰으로 `restore` / `audit` | `FORBIDDEN` |
| USER 토큰으로 `includeDeleted=true` | ACTIVE만 반환 (에러 아님) |
| 잘못된 암호 11회 연속 | `RATE_LIMITED` |
| `차량` 시트에 없는 `vehicleNo` | `VALIDATION_ERROR` |
| `사용자` 시트에 없는 이름으로 `bind` | `VALIDATION_ERROR` |
| 존재하지 않는 `id`로 `update` / `delete` | `NOT_FOUND` |
| 목적지에 `<img src=x onerror=alert(1)>` | 문자 그대로 표시, 실행 안 됨 |
| 8KB 초과 페이로드 | `PAYLOAD_TOO_LARGE` |
| `distance`를 임의값으로 위조 전송 | 무시되고 서버 재계산 값 저장 |

### 11.3 기능·회귀 테스트

- 등록 → 목록 반영 → 새로고침 후 유지
- 수정 → 같은 `id` 유지, `createdAt` 불변, `updatedAt` 갱신, 행 수 불변
- 삭제 → 목록에서 사라짐, **시트 행은 남아 있음**, `status=DELETED`
- 복구(ADMIN) → 목록에 다시 나타남
- 두 브라우저에서 동시 저장 → 두 행 모두 보존, ID 중복 없음
- 필터 적용 → 통계와 CSV가 필터 결과와 일치
- CSV를 엑셀에서 열어 한글 정상, 숫자 열이 숫자로 인식
- 모바일 세로 화면: 터치 타깃, 긴 목적지 줄바꿈, 테이블 오버플로, 수정/삭제 버튼
- 네트워크 차단 후 저장 시도 → 명확한 오류 메시지, 스택 트레이스 없음

## 12. 알려진 한계 (설계상 수용)

정직하게 남기는 것들이다. "미완성"이 아니라 의도한 선택이다.

1. **내부자 사칭 가능.** 이름이 자기 신고이므로 감사 로그는
   "홍길동으로 로그인한 세션이 삭제함"까지만 답한다. 공용 암호 방식(B안)의 알려진 대가다.
   개인 계정이 필요해지면 `사용자` 시트에 해시·솔트 열을 추가하고 로그인 화면만
   교체하면 된다 — 나머지 구조는 그대로 쓴다.

2. **중복 저장 방지 없음.** 저장 요청이 타임아웃된 뒤 사용자가 다시 누르면 2건이
   생길 수 있다. 멱등성 키를 넣는 대신 타임아웃 메시지를
   "저장 여부가 불확실합니다. 목록을 확인한 뒤 다시 시도하세요"로 바꿔 알린다.
   실제로 중복이 잦으면 그때 `clientRequestId` 열을 추가한다.

3. **폴링이 전량을 가져온다.** 약 2,000행(10명 기준 1~2년)을 넘으면 30초마다 오가는
   JSON이 부담이 된다. 화면에 행 수를 표시해 가시화하고, 임계에 도달하면
   서버측 기간 필터로 전환한다.

4. **속도 제한 카운터가 캐시 축출로 초기화될 수 있다.** 500ms 지연이 1차 방어이고
   카운터는 보조다.

5. **개별 세션 무효화 불가.** `TOKEN_VERSION`으로 전원 무효화만 가능하다.
   공용 암호 체계에서는 무효화할 개별 신원이 없으므로 실질적 손실이 없다.

6. **암호 교체 시 전원에게 새 암호를 알려야 한다.** 10명 규모에서는 감당 가능하다.

- 감사 로그에 CREATE/UPDATE/DELETE/RESTORE가 남고 암호·토큰이 없다
- `distance`가 항상 서버 계산값이며 클라이언트 위조가 반영되지 않는다
- 차량 목록이 시트에서 오고 소스에 하드코딩이 없다
- 필터·통계·CSV 세 결과가 서로 일치한다
- CSV가 엑셀에서 한글 깨짐 없이 열린다
- 동시 저장 시 두 기록 모두 보존되고 ID가 중복되지 않는다
- 모바일·데스크톱 모두 조작 가능하고 기존 시각적 정체성이 유지된다
- 콘솔 오류 없음, 기존 기능 회귀 없음
